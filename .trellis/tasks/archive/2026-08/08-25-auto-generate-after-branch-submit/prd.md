# 分支消息提交后自动生成

## Goal

统一 Composer 的发送体验：无论用户是在当前助手叶节点后追加消息、从历史助手消息创建分支，还是编辑历史用户消息并创建分支，消息持久化成功后都应自动生成一次助手回复，不再要求用户额外点击“生成回复”。

## Background

- 普通追加消息当前会在权威用户节点持久化成功后调用 `startGeneration`（`src/features/conversations/hooks/useWorkspaceGenerationController.ts:476-491`）。
- `createBranch` 和 `editNodeAsBranch` 当前只调用 store 的持久化动作，不启动生成（同文件 `:493-501`），因此两个分支入口都会停留在未回复的用户叶节点。
- 现有手动“生成回复”入口仍是生成失败、服务提供商稍后就绪或历史未回复用户节点的恢复路径。

## Requirements

### R1 — 新建分支后自动生成

- 从助手消息发起“从此处创建分支”并通过 Composer 提交时，必须先成功持久化新的权威用户节点，再从该精确节点自动启动一次生成。
- 持久化失败、返回节点未通过现有权威校验、分支意图已失效或用户已切换到其他节点/对话时，不得自动生成。

### R2 — 编辑用户消息为分支后自动生成

- 编辑历史用户消息并创建分支成功后，必须先成功持久化新的权威用户节点，再从该精确节点自动启动一次生成。
- 与 R1 使用相同的服务提供商、只读状态、安全路径、当前选择和活跃生成保护，不得因入口不同产生行为差异。

### R3 — 保留安全与恢复行为

- 服务提供商未配置或未就绪时，分支用户消息仍可按现有规则持久化，但不自动生成。
- 自动生成启动失败时保留已保存的用户节点，并继续提供现有“生成回复”手动重试入口。
- 每次成功提交最多启动一次生成；自动生成已经开始后，手动入口不得造成重复生成。
- 不改变后端/Tauri 命令、SQLite 模式、生成提交协议、分支隔离或历史节点不可变语义。

## Acceptance Criteria

- [x] AC1：从助手消息创建分支并提交后，`createBranch` 先完成持久化，随后以返回的 conversation ID 和用户节点 ID 调用生成，且仅调用一次。
- [x] AC2：编辑历史用户消息创建分支后，`editNodeAsBranch` 先完成持久化，随后以返回的 conversation ID 和用户节点 ID 调用生成，且仅调用一次。
- [x] AC3：两条路径在持久化失败、权威返回无效、服务提供商未就绪、只读/不安全路径、已有活跃生成或等待期间发生导航失效时均不自动生成。
- [x] AC4：自动生成失败后，已保存用户消息仍位于对应分支并可通过“生成回复”重试。
- [x] AC5：普通追加消息和新建对话的现有自动生成行为保持不变；完整前端测试、严格类型检查和 lint 通过。

## Out of Scope

- 选择任意历史用户节点时自动生成。
- 更改“生成回复”按钮的文案、位置或移除该恢复入口。
- 修改后端生成或持久化协议。

## Notes

- This is a lightweight frontend behavior change and remains PRD-only.
