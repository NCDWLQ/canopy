# Tauri Log and Opener Research

## Repository Baseline

- `src-tauri/Cargo.lock` resolves `tauri-plugin-log` to 2.9.0.
- `src-tauri/src/lib.rs` currently installs the log plugin from application setup only for debug builds, at `Info` level.
- `src-tauri/tauri.conf.json` preloads `sqlite:canopy.db`; `tauri-plugin-sql 2.4.0` connects and migrates preloaded databases inside its plugin setup hook.
- The application capability currently contains only `core:default`.
- `src-tauri/Cargo.toml` declares `[lib] name = "canopy_lib"` while the binary is `canopy`. Library log records therefore carry targets starting with `canopy_lib::`, not `canopy::`.
- `src-tauri/src/providers/titles.rs:33` is the only existing product log call. It interpolates `conversation_id` straight into the message.
- `src-tauri/src/conversations/commands.rs:416` (`validate_id`) only rejects blank identifiers, and `generate_from_active_path` uses the same helper for `conversation_id`/`active_node_id`. Those values are therefore arbitrary frontend strings, not validated UUIDs.
- `src-tauri/src/providers/commands.rs:606` (`validate_uuid_v4`) and `:614` (`is_canonical_uuid_v4`) already implement canonical UUIDv4 validation, and `generation_id` at `:513` is generated by Rust with `Uuid::new_v4()`.
- `save_provider` accepts an optional `request.id`; edit/delete/activate/reveal paths receive provider IDs from IPC and use only the non-blank `validate_id`. Provider IDs are therefore not universally Rust-generated at the current command boundary, even though new-provider creation generates one with `Uuid::new_v4()`.

## `tauri-plugin-log 2.9.0`

Verified against the crate source in the local Cargo registry:

- Default targets are stdout and the platform log directory.
- `TargetKind::LogDir` resolves the application log directory and supports an explicit file name.
- `Builder::max_file_size` controls per-file rotation size; the crate default is only 40,000 bytes, so Canopy must configure an explicit larger value.
- `RotationStrategy::KeepSome(n)` retains up to `n` archived files in addition to the active file. `KeepSome(4)` therefore implements the PRD's active + 4 archive budget.
- A one-file total retention policy must use `RotationStrategy::KeepOne`; the crate's rotation path subtracts one from `KeepSome(keep_count)`, so constructing `KeepSome(0)` is invalid for Canopy's policy mapper.
- `FileOpenStrategy::Append` continues the active file across sessions.
- `TimezoneStrategy::UseUtc` is available and matches the stable diagnostic format.
- `Target::filter` and `Builder::filter` both accept a predicate over `log::Metadata`, so persisted output can be restricted to Canopy-owned targets globally and per target.
- `TargetKind::LogDir { file_name }` falls back to the package name when `file_name` is `None`. Rotation pruning (`remove_old_files`) matches archives by that file-name prefix, so an explicit stable file name keeps retention independent of `productName`.
- File output is written through `fern::Output::writer(.., "\n")`. A newline inside a formatted field therefore produces an additional, forgeable log line.
- Plugin setup can return file/directory I/O errors. Installing it best-effort at a dedicated early bootstrap boundary is necessary to prevent logging failure from aborting startup.
- The logger is process-global; repeated real registrations in parallel unit tests can conflict. Keep an inspectable Canopy-owned policy outside the opaque builder and exercise the boxed logger returned by `split` directly for file behavior, without calling `attach_logger`.

### `Builder::split` is the safe best-effort entry point

`Builder::split(app_handle) -> Result<(TauriPlugin<R>, log::LevelFilter, Box<dyn log::Log>), Error>` (`src/lib.rs:817`) performs the same `acquire_logger` work as `build()` but hands the logger back instead of attaching it. `attach_logger(max_level, logger)` (`src/lib.rs:860`) then performs `log::set_boxed_logger` + `log::set_max_level`.

This lets Canopy resolve the log directory, build the sink, and attach the logger from inside its own bootstrap plugin, swallowing any `Error`/`SetLoggerError` at that single boundary. The returned `TauriPlugin` only carries the plugin's `log` IPC command, which Canopy does not want, so dropping it is intentional: the webview-facing command is never registered at all.

`Builder` keeps policy fields private, so a function that only returns `Builder` is not directly inspectable. Tests need a separate `LoggingPolicy` source of truth plus controlled `Folder` targets: an invalid target forces `split` failure, while a temporary valid target lets the returned boxed logger be exercised for format and rotation without global registration.

The crate's `log::Log` surface does not return per-record I/O errors to the caller. Canopy can implement deterministic fallback while building/attaching the logger, but cannot hot-swap the global logger after a runtime write/rotation failure. Any fallback design must therefore be initialization-only and must not promise runtime failover.

Primary source: `tauri-plugin-log-2.9.0/src/lib.rs` from the official Tauri plugins-workspace crate published on crates.io.

## Tauri 2.11.5 plugin initialization ordering and locking

Verified against the crate source in the local Cargo registry:

- `PluginStore` is a `Vec<Box<dyn Plugin<R>>>` (`src/plugin.rs:857`) and `initialize_all` iterates it in registration order (`src/plugin.rs:906`). Registering the diagnostics bootstrap before `tauri_plugin_sql` therefore guarantees it initializes first.
- `AppManager::plugins` is a `std::sync::Mutex<PluginStore<R>>` (`src/manager/mod.rs:193`), and `AppManager::initialize_plugins` (`src/manager/mod.rs:483`) holds that lock across every plugin's setup hook.
- `AppHandle::plugin_boxed` (`src/app.rs:537`) acquires the same non-reentrant mutex.

**Consequence**: calling `app.handle().plugin(...)` from inside a plugin setup hook self-deadlocks, and `Builder::build()` hangs with no error output. The current debug-only registration works only because `Builder::setup`'s closure runs from `fn setup` (`src/app.rs:2530`), after `initialize_plugins` (`src/app.rs:2440`) has released the lock — which is also precisely why it cannot observe SQL preload/migration failures. Dynamic plugin installation is therefore not an available mechanism for an early bootstrap; use `Builder::split` + `attach_logger` instead.

- `tauri::Error::PluginInitialization(String, String)` (`src/error.rs:66`) carries the plugin name and the failure message. Matching the variant allows logging the failing plugin name without formatting the message, which may contain local paths.

Primary source: `tauri-2.11.5/src/{app,manager/mod,plugin,error}.rs` from the official Tauri crate in the local Cargo registry.

## `tauri-plugin-sql 2.4.0`

The plugin's setup hook iterates configured `preload` databases, connects each pool, constructs the registered migrator, runs migrations, and only then manages `DbInstances`. A logging bootstrap registered after SQL cannot observe this startup phase. The diagnostics bootstrap must be registered first; the application run error path should emit a stable safe startup-failure code without formatting the underlying error.

Primary source: `tauri-plugin-sql-2.4.0/src/lib.rs` from the official Tauri plugin crate in the local Cargo registry.

## `tauri-plugin-opener 2.5.4`

`cargo info tauri-plugin-opener` confirmed 2.5.4 as the current published crate compatible with the Tauri 2 plugin line. Official crate source confirms:

- `OpenerExt::opener().open_path(path, None::<&str>)` opens a desktop path in the default system application/file manager.
- `Builder::open_js_links_on_click(false)` prevents the unrelated JavaScript link interception behavior.
- The plugin registers generic `open_path`, `open_url`, and reveal commands, but capability permissions govern webview access.
- Canopy can call the Rust extension from its own no-input command without granting `opener:allow-open-path` to the webview.

Primary source: `tauri-plugin-opener-2.5.4/src/lib.rs` and its published README from the official Tauri plugins-workspace crate.

## Early logging policy persistence

Tauri 2.11.5 exposes `app.path().app_config_dir()` on desktop, allowing the diagnostics bootstrap to read a small product-owned configuration before SQL plugin preload. The existing `app_settings` repository is unavailable at that point because `DbInstances` is managed only after SQL preload/migration completes.

A single truncate-in-place JSON file would make a crash during save destroy the only valid policy. The design therefore uses two bounded versioned slots and always writes the inactive/older slot. Startup reads both and selects the highest valid revision. This avoids relying on platform-specific rename-over-existing semantics and preserves one valid record across a torn write. Each slot is capped at 4 KiB before JSON parsing.

Primary source for the configuration directory: `tauri-2.11.5/src/path/desktop.rs` (`PathResolver::app_config_dir`).

## UI Research

`pnpm exec shadcn info --json` confirms a Vite, React, Tailwind v4, Radix Nova project using Lucide icons. Button, Alert, Breadcrumb, Field, Input, Spinner, and Dialog are already installed. Current shadcn guidance supports:

- outline Button for the directory action;
- `data-icon="inline-start"` on the Lucide icon or Spinner;
- disabled Button plus Spinner for pending state;
- destructive Alert for persistent failure feedback;
- `FieldSet`/`FieldGroup` for related settings, responsive `Field` + `FieldContent` for labelled numeric inputs, and paired `data-invalid`/`aria-invalid` + `FieldError` for accessible validation;
- semantic tokens and existing settings layout rather than custom colors/components.

No new shadcn component is required for the MVP.
