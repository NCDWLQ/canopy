# 调研：主流产品的对话标题生成实践

日期：2026-09-08。用途：评估 canopy 标题生成提示词与触发时机是否需要修改。

## 主流实践摘要

| 产品/项目 | 输入内容 | 触发时机 | 提示词要点 | 防覆盖/幂等 |
|---|---|---|---|---|
| OpenHands SDK (`title_utils.py`) | **仅首条用户消息**，截断到 1000 字符 | 会话早期一次性 | system 说明任务；user 要求“只返回标题，不要引号或解释”，最大 50 字符 | LLM 失败返回 None，静默回退 |
| claude-live-title (Claude Code 插件) | GOAL=首条用户消息 + 头尾用户消息 + 截断 300 字符的最新回复 | **UserPromptSubmit 即触发（与回复并行）**，Stop 事件兜底 | 首条用户消息锚定标题意图，防止长会话漂移 | 节流到一次性调用 |
| multica (PR #5141) | 首条用户消息 | 检测到**首条人类消息插入前**即触发 | 短 system prompt + 默认小模型（gpt-4o-mini） | **CAS 更新**（`UpdateChatSessionTitleIfCurrent`）：生成期间用户手动改名不被覆盖；最多标题一次 |
| garcon | 首条用户 prompt | 一次性 one-shot 查询 | — | `setSessionNameIfAbsent` 幂等写入 |
| ChatOllama 博客方案 | 首条用户消息 + 首条 AI 回复摘要 | 首条回复完成后 | 按语言分模板（en/zh），最大 50 字符，无引号无格式 | 关键词提取 → 日期标题 的多级回退 |

## 共识结论

1. **仅首条用户消息是主流且可行的输入**。OpenHands、multica、garcon 都只用首条用户消息。ChatOllama 指出“仅首条用户消息可能过短（如‘帮我个忙’）”，但实践中配合好的提示词足够，且 canopy 前端已有 40 字符占位标题兜底。
2. **与回复并行触发是已验证的模式**。claude-live-title 在用户提交 prompt 的瞬间就开始生成标题；multica 在首条消息插入时触发。回复完成时标题通常已就绪。
3. **提示词关键要素**（评估现有提示词是否需要修改的基准）：
   - 明确“只返回标题本身”，禁止引号、解释、前缀；
   - 明确长度上限（30–50 字符级）；
   - 要求**使用用户消息的语言**；
   - 输入做截断与噪声清理；
   - 用小/快模型，限制 max_tokens。
4. **并发窗口下必须防覆盖**：并行化后标题可能在用户手动改名后才返回 → CAS（仅当标题仍是触发时观察到的值才写入）是主流解法（multica、garcon 均如此）。
5. **失败静默**：标题生成失败只记日志，不打断聊天、不向用户报错。

## 对 canopy 现有实现的评估

- 现有 `TITLE_SYSTEM_INSTRUCTION` 仍以“assistant 作为辅助上下文”为前提，user payload 固定包含 `<assistant>` 块 → **必须改写**为仅用户消息。
- 现有触发在首条回复 `Completed` 之后 → 与回复是串行的，需前移到生成开始。
- 现有门控“assistant 恰好一条”在并行模式下失效（触发时 assistant 还不存在；重试时可能多于一条）→ 需换成“标题仍是占位值”CAS 语义。
- 现有的转义、截断（2000 字符）、`clean_title` 后处理、`max_tokens=256`、低推理档位，与主流实践一致，可保留。
